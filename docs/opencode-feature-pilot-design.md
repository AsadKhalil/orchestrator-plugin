# OpenCode Feature Pilot — design brief

This is the original design proposal, prepared 2026-11-11. The repository now contains an incomplete prototype; see the README and implementation progress for current status. The working package name's availability has not been checked.

## Purpose

Extend OpenCode Desktop with one plugin that turns a feature requirement into a clarified brief, an approved plan, implementation, independent review, and a final diff or an explicitly enabled draft PR. Pick models dynamically using task capabilities, benchmark evidence, actual endpoint prices, available credits, and configured spending limits. Explain each recommendation and measure the cost of accepted work against subscriptions.

This reuses OpenCode's sessions, model integrations, tools, permissions, worktrees, storage, and desktop extension points. It is not a new agent framework, model gateway, editor, subscription reseller, or inference service.

## Requirements already established by the user

- Desktop plugin, suitable for publishing on GitHub.
- No hardcoded model assignment to any workflow stage; users may pin a role to one model or permit routing within their selected list.
- Exactly three workflow roles: planner, coder and reviewer. Initial problem expansion and clarification belong to the planner role; reasoning effort is an independent selection dimension.
- Users select allowed models for each role from their available OpenCode integrations. Every owned model call, including debugging and visual subtasks, stays inside the owning role's selection. One selected model fixes the role; multiple selected models permit cost-based routing within that list.
- Consider connected hosted providers and local runtimes, including Ollama. Provider support follows OpenCode and the connected model's actual capabilities.
- Use intelligence evidence and cost to recommend a model for a task. models.dev alone is insufficient because it does not supply an intelligence index.
- Expand the initial problem into a useful brief covering relevant real-world scenarios, architecture, scale, security, monitoring/logging, and SEO/AEO/GEO.
- Frontier-quality planning and review; economical qualified implementation. Planner researches and asks material questions without editing source code.
- Approval before implementation in supervised mode; automatic stage progression when the user explicitly enables autonomous/full-access operation.
- A different frontier reviewer, with bounded repair cycles.
- Understand the difference between tools and model capabilities: capturing an image is a tool operation; interpreting it requires image input.
- Compare costs fairly against approximately $100/month subscriptions, using current official sources.

## Proposed implementation choices

These are recommendations, not preferences the user has already chosen.

- One TypeScript package with an OpenCode server entry and a Solid desktop GUI entry; reuse the host UI components and Vite GUI preset. No hosted backend in the initial release.
- Target OpenCode Desktop and `@opencode/plugin` **2.2.7**, pinned together. Validate packaged compatibility before depending on experimental APIs. macOS is the first manual test target; Windows/Linux support is claimed only after smoke testing.
- One active feature run per worktree. Distinct worktrees may run concurrently, sharing this host's monthly budget reservations.
- Supervised mode is the default. Autonomous mode is explicit per run/profile and cannot override an organization deny rule. Ambiguity still pauses either mode.
- Quality floors, feature/monthly dollar budgets, and a maximum output allowance are required onboarding settings, not guessed values. Provide no silent numeric intelligence default. The user's earlier “25” was an example.
- Planner/reviewer quality floors cannot be lower than the coder floor. Show the current score distribution so the user can choose what qualifies as frontier. Do not label an arbitrary threshold an objective definition of frontier.
- Initial review plus at most **two repair rounds**, hence at most **three review passes**. Keep the reviewer model/version and rubric fixed through a feature unless unavailable; replacement pauses and is recorded. Retry a transient provider failure at most **two** times, honoring Retry-After; bill and reserve all attempts. Do not retry authentication/invalid-request errors automatically.
- Default completion is a local diff. A draft PR is an optional per-project setting requiring explicit authorization of the remote and branch policy. No merge/deploy automation.

## Release prerequisites and evidence

1. **Host feasibility:** prove desktop panel loading, cross-provider session switching, role permissions, usage extraction, cancellation, and durable recovery against 2.2.7. If a documented capability does not work, record the smallest host change needed and revise the plan before broadening into an app fork.
2. **Benchmark rights:** AA terms sections 2.4–2.5 constrain redistribution and public model-selection products. Neither bring-your-own-key nor a third-party feed is assumed to grant permission. Obtain terms covering the intended integration before a public AA-backed release. Build ingestion against synthetic fixtures meanwhile; do not ship copied AA datasets.
3. **Actual cost evidence:** a catalog price or host cost estimate is not a provider invoice. Label provenance and uncertainty. Do not market measured savings until matched-workload runs exist.

OpenRouter's live catalog was observed to expose `benchmarks.artificial_analysis.intelligence_index`. Its docs offer intelligence, price and modality filters. Coverage, index version and permitted reuse need explicit treatment; absence of version metadata must be visible. Direct AA v2 provides version metadata. models.dev supplies identities, capabilities and catalog prices, not a substitute intelligence score. Current AA Coding/Agentic Index fields are discontinued/null; do not use them for ranking.

## User experience and feature lifecycle

One desktop panel contains a new-feature form, run progress, the requirement/plan, model recommendations with exclusions, review findings, and costs. Settings contain connected-source status, role quality floors, spending limits, permission mode and optional PR destination. Never ask a user to choose a model merely to run a shell command.

### How a feature reaches different models

The plugin's New Feature form is the entry point for this workflow. Sending a message in an ordinary OpenCode chat continues to use that chat's selected model. The plugin does not silently intercept ordinary chats or make the selected model forward every message.

The plugin coordinator is ordinary TypeScript running in OpenCode. Before a stage's first inference, it creates an owned OpenCode session, applies its permissions/budget controls, explicitly selects the policy's model and supported reasoning variant, and submits that stage's prompt. Clarification replies and plan feedback return to planner-role sessions; approved implementation starts a coder session; review starts an independent reviewer session. A clarification and planning session may be continued together only when the selection and permissions are unchanged. One panel presents the combined timeline and exposes links to these underlying sessions; they are not assumed to share conversational memory.

The canonical requirement, user answers, approved plan and hashes are passed explicitly. Review also receives the actual diff and validation artifacts. This preserves decisions without copying every previous tool transcript. Changing a task after approval pauses progression for a revised plan. A user changing the native model picker for an owned running session is treated as an explicit override requiring policy/budget revalidation; it is never silently ignored or allowed to falsify recorded selection.

The documented implementation uses session creation and `session.switchModel` before `session.prompt`. Selection is per session. These calls are verified by the first host smoke test, including a different model selected in an unrelated normal chat. There is no new proxy or mandatory paid coordinator model.

### Model list and new releases

The runnable list comes from models supported/enabled by OpenCode and available to this project, enriched with allowed benchmark and pricing data. Display model/version, serving provider, originating vendor, score/version, vision/tools, context, price, data age and eligibility reason. Candidates known from connected catalog feeds but absent from the host's runnable inventory may appear as unavailable; discovery never means permission or capability to execute.

Each role has a user-selected allowed-model list and optional allowed reasoning variants. Availability is not authorization to use every connected model. Intersect the role list with capability, benchmark, effort, permission, vendor and budget requirements before ranking. A fixed A/B/C assignment uses only A for planning, B for coding and C for review; it remains subject to those requirements. If no permitted candidate can handle screenshots or another required task, pause with the missing capability and let the user amend that role's list or task. Never fall back outside the list. New catalog models appear as unselected suggestions, including cheaper releases; adopting them requires a user selection change. Record selection revisions for each run, and revalidate any mid-run change at a safe boundary.

The picker defaults to **Available in this project**, using the host's enabled models and available providers, including configured local/custom endpoints. A **Browse catalog** filter can show other entries known to the host or permitted feeds as unavailable or requiring connection; it is not a claim to list every provider on the internet. Provider setup remains in OpenCode. Search/filter by provider, originating vendor, role eligibility, modality and selected status. Rank model/provider/effort options across providers; do not give a provider one universal price or intelligence rank. Preserve different serving endpoints for the same model as different price/auth routes.

Offer three display sorts: **Recommended** (eligible options by estimated task cost, with exclusion reasons below), **Lowest cost**, and **Highest intelligence**. Lowest cost explicitly chooses a basis: estimated task/reference-workload cost, input USD per million tokens, or output USD per million tokens; never an unexplained blended price. Before a task exists, a reference workload must be user-entered or clearly labelled, otherwise show unit rates only. Highest intelligence compares the selected benchmark version and matched tested configuration; incompatible versions form separate groups and unknown scores appear last. Unknown prices also appear last, not as zero. Changing a table sort never edits role selections or changes the run's cheapest-qualified routing policy.

Each row shows model/version, serving provider/auth route, allowed effort, intelligence score and tested effort/version, required capability fit, input/output rates and applicable cache rates, estimated task cost when available, data age and selection status. A model row can expand to its supported variants to avoid an enormous flat list. Distinguish **available**, **selected for this role**, and **eligible for this task**. Example reason text: “Selected for coder; supports image input; benchmark matches high effort; lowest estimated cost among qualifying selected options.” A role's initial quality threshold remains a user choice, not an invented universal boundary.

Refresh on plugin activation when the cache is expired, after a provider/account/local inventory change, and on a user Refresh action; while the host is running, check the 24-hour refresh interval. Re-fetch source data before reloading/recomputing inventory; a host reload alone does not discover announcements. No background refresh runs while the app/server is stopped. Keep the last valid snapshot on failure, with its age visible.

A newly released model progresses through discovery, confirmed host/account availability, verified capabilities/prices, benchmark mapping/version and policy eligibility. Until its score is available it is labelled awaiting benchmark and is not automatically selected under a score threshold. If a new model uses a supported provider/protocol and the feeds expose the required data, it becomes eligible without changing hardcoded model names or releasing the plugin. New protocols, unsupported capabilities or changed authentication may require an OpenCode/provider integration update. Listing a local model does not download it or grant hosted access.

Refreshes update future recommendations, not an in-flight inference. Choose from the current validated snapshot at the next stage boundary, reserve using current rates, and record the snapshot; the reviewer remains pinned throughout repairs. A provider retiring a selected model pauses/fails over under the recorded policy rather than silently changing the run. Prices are evidence snapshots, not guaranteed future billing quotes.

1. **Inspect and clarify.** Read the selected repo; identify its stack, instructions and existing validation. If the working tree is dirty, ask which clean committed baseline to use; never reset, stash or discard changes automatically. Convert the requirement into acceptance criteria and questions. Cover errors, empty states, permissions, migrations, accessibility, real browser journeys, scale assumptions, security, redacted logs, monitoring and rollback when relevant. Mark SEO/AEO/GEO not applicable with a reason for non-public features. No promise of rankings or universal test coverage.
2. **Plan.** A dynamically selected qualified planner lists affected files/areas, ordered work, observable acceptance criteria, test commands, expected artifacts, relevant non-functional requirements, risks and rollback. Questions are structured, shown in the panel, and answered before advancing. Each step has a stable ID, dependencies, tool/capability requirements, declared input/output resources and a completion condition. Include approved validation commands, deadlines, and readiness probes for long-running services. Unspecified dependencies or resource effects imply sequential execution, not assumed independence.
3. **Approval.** Canonical requirement, questions/answers and plan are saved in host plugin storage, with a hash and base commit. Supervised mode waits for approval of that exact hash. Autonomous mode records policy authorization for the hash. A changed requirement, scope or plan invalidates prior approval. Exported Markdown is a copy, not the authoritative plan.
4. **Implement.** Create an isolated host worktree from the selected base and select the least expensive eligible coder for the estimated workload. Provide the exact approved requirement and plan, independent of previous conversation context. The coder cannot expand scope silently. Unexpected necessary work returns a plan amendment for approval/policy evaluation.
5. **Validate and review.** Execute approved validation commands through the host's execution/permission path; capture exit code and a bounded output artifact. The reviewer receives the original requirement, plan, full diff including untracked changes, relevant source, and validation results. It cannot edit source. Review must identify violated acceptance criteria or demonstrable defects and evidence. Style preferences and speculative enhancements are advisory.
6. **Repair or stop.** The coder addresses blocking findings; repeat approved validation and focused review. At the round/budget limit, return unresolved findings and the diff with status `needs_attention`; never call it accepted. New blocking findings must be regressions, previously missed concrete failures, or unmet approved criteria, not a changing style rubric.
7. **Finish.** Successful validation plus reviewer approval yields `ready_for_acceptance`. User acceptance is recorded separately for cost-per-accepted-feature reporting; automated completion is not fabricated human acceptance. If pre-authorized, prepare a commit and draft PR for only this run's branch/diff. Record the link and prevent duplicate PRs on resume.

Persist these states: `clarifying`, `planning`, `awaiting_approval`, `implementing`, `validating`, `reviewing`, `repairing`, `ready_for_acceptance`, `accepted`, `needs_attention`, `cancelled`. `needs_attention` includes a reason and a saved resumable checkpoint. Every transition has an expected run revision so duplicate events or windows cannot advance it twice.

## Dynamic selection contract

Represent an option as **provider endpoint + exact model/version + reasoning variant**, with originating model vendor, available authentication route, capabilities, context limits, rate schedule, price provenance, score provenance and benchmark version. Resolve identities with explicit canonical IDs/validated aliases; never fuzzy-join model names or assume local quantizations share hosted scores.

### Three roles and reasoning effort

The three roles are planner (including clarification and brief expansion), coder (implementation and fixes), and reviewer (independent evaluation). They are policies applied to host sessions, not three separate provider API implementations. Model calls, credentials and protocol translation use OpenCode's existing integrations; the plugin's own external requests fetch permitted price/benchmark metadata. Supported subscription sign-in routes retain their actual billing/allowance rules and are not treated as transferable API credit.

Select the tuple **role + provider/auth route + exact model/version + reasoning configuration + service tier**. Enumerate only reasoning variants supported by that model's host/provider metadata. Preserve both the OpenCode variant ID and its resolved native controls, such as effort, thinking mode or token budget; a custom variant named `fast` does not prove that it changes service tier. Missing effort controls mean fixed/default reasoning, not invented `low`/`medium`/`high`/`xhigh`/`max` options. The same effort label is not assumed equivalent across models or vendors.

A model/effort pair does not intrinsically belong to a role. Workflow state establishes planner/coder/reviewer ownership; the approved step supplies its task requirements. The plugin then checks the user's role list, exact supported variants, capability/context fit, matched quality evidence, reviewer independence and budget before cost ranking. The same pair can be eligible for several roles, subject to per-run independence. Support a fixed model with fixed effort, a fixed model with automatic choice among permitted efforts, or several selected models with automatic model/effort choice. “Auto” never invents missing evidence or grants use of an unselected model. This is ordinary selection code using the existing planner's validated step descriptions, not another paid model deciding each shell call.

Compare eligible model/effort combinations by estimated total task cost. Do not hardcode high/max for the planner or low for the coder, and do not always try low then repeat at higher effort. The model's benchmark must match its tested reasoning configuration where documented. A score measured at max cannot certify low; retain unavailable/unknown effort-specific quality as unknown and exclude it from strict automatic score qualification unless directly supported by matching evidence. User-approved exceptions remain explicit overrides. Do not fabricate per-effort intelligence scores from a model-level score.

Higher effort can increase reasoning tokens, response/tool-call volume, subsequent input, latency and retry probability; it is not a universal price multiplier. Separate the documented rate schedule from estimated units. Keep reasoning effort distinct from Fast/Ultrafast/Batch or other service tiers, which can change rates. Use provider usage semantics to avoid double-counting reasoning already included in the generated-output total. Record visible output and reasoning counts when available, total billed output, actual/estimated cost, effort and service tier for every attempt. Provider caps on generated output must include reasoning where that provider counts it. Missing reasoning breakdown is unknown, not zero.

If effort-specific workload history is absent, display a conservative estimate/range and the configured total-output reservation rather than a precise predicted bill or invented max-vs-medium multiplier. The reviewer is pinned by model/version and reasoning configuration throughout its repair cycle. A coder escalation changes the recorded configuration, reruns eligibility/budget checks and stays inside the same repair cap. Changing effort never resets the repair counter.

Desktop recommendations show role, model/provider, effort, benchmark tested effort/version, input/output rates, expected billable units, estimated gross/cash cost and uncertainty. A supported subscription route may show no incremental API charge in OpenCode while consuming allowance; display that fact and any unknown quota cost, not “free inference.”

Eligibility requires a connected allowed provider, known required capabilities, sufficient context/output limits, a permitted current benchmark matching the configured quality floor, and a priced execution route within budget. Missing required facts exclude automatic selection and appear with a reason. An unknown benchmark index version is ineligible unless independently verified source metadata establishes the snapshot's version; it is not guessed from the fetch date. A user may explicitly run an unscored/unknown-version model in supervised mode, but that run is labelled an override and never claimed to satisfy the score policy.

Reviewer model vendor must differ from both planner and coder vendors; hosting two vendors through the same gateway is allowed. If no eligible reviewer remains, ask for a policy/provider change. Do not silently relax the vendor or quality rule.

Rank eligible choices by estimated incremental cash cost for that stage after usable route-specific credits. Show gross cost separately. Estimate with the actual prompt/context size where possible, a stated output allowance, cache eligibility, provider rate tiers and known tool/image charges. Without trustworthy cache evidence, assume cache miss. Unknown metered components prevent a “cheapest verified” claim. Break ties deterministically by better quality, lower estimated latency when available, then canonical ID.

Choose at stage boundaries. Capability changes within a stage may create a bounded host subtask, such as screenshot interpretation; its model uses the same eligibility policy and returns a factual artifact to the ongoing stage. Include its cost. Do not build a model switch for every tool call. Preserve active context, avoid unnecessary cache loss, and record any failover. Planner and coder may coincidentally select the same model; never force a more expensive alternative merely to make the stage names different.

### Roles, task types, capabilities and tools

Keep three accountable roles. A task type describes the work inside a role; a capability describes what its selected model must support; a tool performs an operation. The plugin tracks dependencies and outcomes using ordinary code. It does not need a fourth paid model to watch other models or wait for commands.

| Task or operation | Owner | What needs model inference | Required tools/capabilities and completion evidence |
|---|---|---|---|
| Clarification and scenario expansion | Planner | Resolve ambiguity and write acceptance criteria | Repo reading/questions; answered material questions |
| Repo and current-document research | Planner, or the active role for a bounded question | Explain relevant evidence | Search/read/web tools; source/file references and dates |
| Architecture, security, scale and migration planning | Planner | Assess tradeoffs relevant to the requirement | Reasoning/context; approved constraints and rollback |
| Implementation, tests and documentation | Coder | Author changes within the plan | Coding/tool calling; diff and executable checks |
| Debugging | Coder | Form and test a cause for a concrete failure | Logs/trace/source; reproduction, fix and recheck |
| Test execution, build, lint or typecheck | Plugin invokes approved host tools | None for launching a known command and recording its outcome | Shell/tool access; exit status and artifacts, with actual validated content version |
| Screenshot capture | Plugin invokes approved host tools | None for capture itself | Browser/capture access; image artifact and viewport/page identity |
| Screenshot, diagram or scanned-document interpretation | Owning planner/coder/reviewer | Interpret visual evidence | Supported image/PDF input and task evidence; findings tied to source images/pages |
| Browser interaction and real-user journeys | Coder; independent evidence for reviewer | Decide actions only when the approved test is not already scripted | DOM/control tool protocol; vision for pixel-based actions; assertions and artifacts |
| Independent review, including security/performance/accessibility criteria | Reviewer | Judge requirement, plan and evidence | Read-only context; concrete findings and verdict |
| Background process status and readiness | Plugin invokes host status/probe facilities | None for process state, exit code, deadline or deterministic health checks | Owned job handle; running/ready/succeeded/failed status |
| Large-log extraction and context summarization | Owning role | Summarize only when filtering and direct reads are insufficient | Host search/compaction; preserve canonical plan and link raw artifacts |

Security review, accessibility, database changes, SEO/AEO/GEO, performance and multilingual work are task tags and acceptance criteria, not permanently running agents. Apply them only where relevant. For structured plans/findings, require validated schema output (native structured output where supported, otherwise the existing bounded parse/correction path). Neither tool-call support nor a large context window establishes reliability; task-specific evidence remains separate from the general intelligence score.

AA's current methodology describes the Intelligence Index as a broad, primarily text-based English evaluation and evaluates visual reasoning separately. Therefore preserve task-specific evaluation results or observed local outcomes, with their tested harness/model/effort, separately from the role's AA floor. Show missing task evidence as unknown; if a task-specific threshold is configured, missing evidence cannot satisfy it. Do not invent a vision, debugging or security score by relabelling the overall index. Supported attachment formats are the intersection of OpenCode transport and the selected model/provider; a model's advertised audio/video/PDF ability alone is insufficient. [AA methodology](https://artificialanalysis.ai/methodology/intelligence-benchmarking), [OpenCode attachment support](https://opencode.ai/docs/attachments/).

Debugging is a bounded coder task, not an unending fourth stage. Preserve the failing command, input version, exit status and relevant logs. A permissions/authentication/quota failure is not automatically a code defect. Allow at most one diagnostic helper invocation per repair round, inside the coder's allowed-model list, permissions and budget; it may propose a patch, but only the main coder session writes. Every fix attempt after failed validation or blocking review consumes the shared two-repair limit, even if review has not yet begun. Evidence-only diagnostics do not reset it. A needed scope change returns to the planner and invalidates approval. Track every materially contributing planner/coder model vendor so reviewer independence also covers diagnostic and visual helpers.

Context summaries and other auxiliary model calls inherit the owning role's allowed list and budget; no host auxiliary fallback may silently use an excluded model. Preserve exact requirements, approved hashes and acceptance criteria outside lossy summaries. Reuse host compaction, with its behavior verified in Task 1; do not build a separate memory service. Image generation, audio/video processing, embeddings and reranking are distinct possible capabilities, but dedicated integrations for them are outside this first coding-workflow release. If a plan needs an unsupported operation, report the gap instead of pretending a screenshot reader can perform it. [OpenCode compaction](https://opencode.ai/docs/compaction/).

### Background work and the next task

OpenCode documents `shell` and `subagent` calls with `background: true`, completion notifications, and host events/session controls. Reuse these facilities and verify their handles, completion/cancellation semantics and plugin access on pinned 2.2.7. A documentation claim is not a completed integration test. Native notifications may trigger paid model turns; observe, budget and deduplicate those turns instead of promising zero background cost. A shell process is not a background LLM request, and neither is a provider's discounted batch-inference service. [OpenCode tools](https://opencode.ai/docs/tools/), [plugin server API](https://opencode.ai/docs/build/plugins/server/).

The plugin records each approved step and owned job with dependencies, content version, resources, host handle, deadline, artifact references and status. Use `pending`, `running`, `ready` (service only), `succeeded`, `failed`, `cancelled`, `timed_out`, or `unknown`; a spawned job is not a successful job. Deduplicated host events advance runnable steps at safe session boundaries. Use bounded host status/probe checks only where events are insufficient; never repeatedly ask an LLM whether a command has finished. If no independent task is runnable, wait without additional inference.

Example: implement an endpoint, start its approved tests, and meanwhile research documentation without editing the checkout under test. Once the tests pass, release dependent work. To edit during testing, first validate an immutable snapshot in a separate host worktree; a result remains attached to that version. Initial release keeps one writer per worktree and no simultaneous writer helpers. If tested content changes, previous results are stale for readiness and affected checks must run again. Unknown resource effects serialize work; disjoint filenames alone do not prove independence.

Dev servers reach readiness through the approved probe, not by exiting. Browser tests can start after readiness while the server stays running; an early exit invalidates dependent work. Use explicit command/probe deadlines, bounded log retention and owned-process cleanup. Stop cancels owned jobs and sessions, confirms cleanup where supported and preserves artifacts; it never kills unrelated user processes. On reconnect, reconcile host handles and recorded versions. Missing or ambiguous handles produce `unknown`/`needs_attention`, not blind resubmission. Work continues only while the owning OpenCode service and required tools remain available; closing Desktop is not a guarantee of continuation, and visible-browser operations can require an open focused desktop tab.

Initial concurrency: one active model task per feature and one owned background shell job, with independent read-only model work allowed while that job runs. A dev server occupies the shell-job slot; a foreground browser test may use it. Higher concurrency and simultaneous model specialists are deferred until measurements justify them. Background execution must never bypass plan approval, role selection, dependency checks, global reservations or the repair cap.

No full-access setting removes the planner/reviewer source-edit restriction. Deny arbitrary shell, editing, subagent spawning and side-effecting MCP/browser tools in those roles. Allow only tested read/search/question operations; execute validation separately through an authorized executor. Treat repo/web/tool text as untrusted data: model output cannot rewrite permission, budget, source-authorization or approval policy. Host tools are not an OS security sandbox: existing plugins and the local machine remain part of the trust boundary.

## Prices, benchmark data and cost comparisons

Use OpenCode's enabled catalog as the inventory. Enrich capabilities from models.dev/provider docs. Benchmark connectors support permitted direct AA v2 or the permitted OpenRouter catalog; settings must select a source and disclosed index version policy. Do not blend incompatible benchmark versions or compare them as a time series without a methodology change marker.

Use structured endpoint pricing where available. For direct OpenAI, Anthropic, Gemini and DeepSeek, maintain normalized rates checked against official pricing pages, with source URL, checked-at time, currency, unit, conditions and a parser/validation fixture. Extra providers use documented endpoint/catalog rates and are labelled accordingly. Never call community catalog prices “officially verified.” Refresh cache after 24 hours; data older than seven days is excluded from unattended selection pending refresh or an explicit recorded override. A provider error preserves the last valid data and marks it stale; it never creates a zero price.

Normalizing prices must preserve input/output, reasoning billing, cache read/write/storage, image tokenization or per-image costs, tool requests, long-context tiers, batch/standard routes, time-of-day rates and applicable region/currency. Do not use batch discounts for interactive execution. Local inference shows a zero hosted API charge plus separately supplied local operating costs, not a claim that hardware is free.

Persist per-attempt usage with stable message/request IDs, stage, endpoint, variant, token counts/units, gross cost, credit allocation, estimated cash cost, provenance and timestamp. Reconcile provider-reported cost when available; otherwise label computed costs as estimates. Capture title, compaction and any child-model calls belonging to the run. Deduplicate streaming/replayed events. Do not store prompts, source, raw token content or API keys in analytics logs; local requirement/plan artifacts are intentionally retained as workspace data, with a delete action.

### Daily and monthly usage

Add a Usage view backed by the existing ledger, with Today and a selectable calendar month. Show a daily spending chart plus an accessible table, month-to-date/selected-month totals, remaining monthly budget, and pending reservations separately. Break down usage by project/feature, provider, model/effort and role. Include failed runs, debugging, review repairs and auxiliary calls, not only successful features. This first version measures this plugin's runs on the owning host, not all OpenCode chats or spending in other apps/devices.

Store the request-start timestamp in UTC and bucket each attempt once in the user's chosen IANA reporting timezone, initially the device timezone and visibly labelled. A request crossing midnight belongs to its start day. Sum unrounded decimal values; round only for display. Late usage/cost corrections update the original day/month rather than appearing as new spending today. Calendar-month reporting stays distinct from provider subscription billing cycles and credit expiry. Reporting timezone changes do not reset the existing spending-limit window or ledger.

Show gross metered cost, credits applied and estimated cash cost as distinct values, preserving provider-reported versus calculated provenance. Pending reservations are not incurred spending. If any charge is unknown, label the period total partial and show its unknown-request count; never replace missing costs with zero. Subscription allowance consumption is not converted into invented API dollars. Fixed subscription fees and local operating costs remain explicit comparison items rather than being silently distributed across the daily API chart. No paid model calls are needed to compute these aggregates.

For each billing cycle show:

- API-only replacement: gross metered usage plus operating costs.
- Keep subscription: fee plus usage not covered by eligible remaining credits plus operating costs.
- Native subscription: fee plus actual overages and the extra independent review cost required for an equivalent workflow. Unknown native capacity stays unknown.

Credits are provider/route/cycle specific and cannot offset another provider. Shared-org use outside this plugin reduces availability; if balance cannot be verified, require an entered balance and label it unverified. First-cycle proration, expiry and other spending matter. Include billed calls from unsuccessful runs in cost per user-accepted feature. Show completion rate, review rounds and elapsed time beside costs. A subscription includes non-coding benefits; do not claim financial equivalence beyond the measured workflow.

Current documentation says eligible Claude Max and ChatGPT Pro $100 plans can include $100 API credits after claiming, with exclusions. Treat these as dated plan data, not permanent constants. No automatic extraction of private account billing data or subscription-login reuse as arbitrary API credit. GitHub exports contain methodology, prices/dates and aggregate measurements only; no secrets, source snippets or benchmark redistribution without permission.

## Reliability and spending controls

All limits apply to this plugin's runs on its owning host, not unrelated applications or other devices. Reserve a conservative amount before each paid request, reconcile afterwards, and refuse another request when the remaining run/month budget is insufficient. Reserve gross metered cost by default. Credits may reduce a hard reservation only when the provider verifies and guarantees an exclusive reservation of that balance; a manual balance or a fresh but shared balance is insufficient. Such balances can inform clearly labelled cost estimates only. Bound output/tool loops and retry attempts; include in-flight reservations across simultaneous worktrees. If the host/provider cannot supply a defensible upper bound, expose this limit and refuse unattended hard-budget mode for that route. Provider-side caps remain the final billing control; cancellation cannot undo an already billed request.

Persist checkpoints before issuing side effects. After a crash, reconcile host session IDs and worktree state instead of resending a prompt blindly. Ambiguous in-flight requests pause with `needs_attention`; never replay a potentially destructive script or PR operation automatically. Stop interrupts the relevant owned sessions, releases only known unused reservations, and preserves the diff. Do not alter unrelated sessions or global model defaults.

## Acceptance and exclusions

The release must demonstrate all workflow stages using at least two hosted vendors and one supported local runtime, with model IDs appearing only in user/provider data and fixtures. Verify permission enforcement with a planner trying to write through both edit and shell, approval-hash invalidation, repeatable recommendations, unavailable vision, review-loop termination, billing deduplication, credit expiry, crash recovery, and separate worktrees.

Test a screenshot-dependent UI task and a backend task against fixed acceptance criteria. Compare dynamic routing with a single qualifying frontier baseline on the same clean repo snapshots; record all retries and failures. Report only observed results, not a universal savings percentage. GitHub publication includes setup, limitations, fixture-only tests, privacy and license notices; actual remote publication requires user authorization at execution time.

Excluded from the initial release: a new agent runtime/gateway, a cloud account system, training a router, automatic benchmark scraping, access through unsupported subscription credentials, a custom browser/shell, public benchmark mirrors, payments/subscription purchasing, auto-merging and deployment. These exclusions do not remove any requested core stage or intelligence-based routing requirement.
