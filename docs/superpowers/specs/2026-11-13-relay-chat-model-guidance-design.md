## Intent and why

The owner uses many providers and models through OpenCode and does not want to decide which model fits each message. They type `/relay` and a question in the normal OpenCode chat. Relay works out what kind of request it is, switches the chat to the model the owner chose for that kind, and the answer appears in the same chat. Images and `@` files keep working, because it is still OpenCode's chat.

There are three kinds of request, called modes, in the owner's words: plan, execute, review.

The owner pointed to Google's Gemini Decision 1, released on 11 Nov 2026. It writes no text. It is given a question and a fixed list of choices, picks one, and says how sure it is. Google names model routing as one of its uses.

The owner also lets the answering model hand parts of a job to helpers (OpenCode calls them subagents). A helper that checks work should use the Review model. And a review should come to an end: the owner has seen reviews that find new issues in every round.

What Relay stops being: a pipeline that runs a whole feature from the side panel (plan approval, a coder in a separate copy of the project, a reviewer, a draft pull request). The owner does not want that as the product. Its code stays in the repo for now, with its screens hidden.

## The flow

1. Once, in Relay's side panel: for each mode the owner picks one or more models, each with an effort and one line saying what to use it for, with price and intelligence index beside each model. They also pick the model that makes the choice (the decider).
2. In the chat they type `/relay why is login slow? @src/auth.ts`, with or without an image.
3. Relay asks the decider, in one request: is this plan, execute or review, and which "use it for" line of that mode fits best?
4. Relay switches the chat to that model and sends the message, unchanged, into the same chat. When no line fits clearly, the chat keeps its model if it is one of that mode's models; otherwise the first model of the list is used.
5. The answer appears in the chat, from that model.
6. Next time, `/relay` chooses again. A message typed without `/relay` goes to whatever model the chat has now.
7. If the answering model starts a helper to check its work, that helper runs on the Review model and follows rules that make the review end.

## Goals

1. `/relay <question>` in the normal chat is answered in that chat by the model chosen for the question's mode.
2. The text, `@` files and images reach the model exactly as typed.
3. The person can see which mode and model were picked, how sure the decider was, and the reason whenever nothing was switched.
4. The side panel is settings only, and every model in it is shown with its price and index.
5. A wrong or missing decision never drops the message. An unsure or missing decision never moves the chat to an agent that can change files.
6. A helper that checks work runs on the Review model. A helper that writes code runs on the chat's model, which is the Execute model after `/relay` has chosen Execute.
7. A review ends. It does not find new issues round after round.

## Non-goals

- No routing of what the person types without `/relay`. The host's hook for changing the model of one request is experimental and only works inside one provider. A helper that checks work is the one exception (see "How a check gets the Review model").
- No side-panel run. The pipeline's screens are hidden.
- No second chat, and no provider, login or local-model code. OpenCode owns those.
- No spending cap on chat messages, and no second cost total. They are the person's own chat, and OpenCode already shows each chat's total cost.
- The decider does not choose the effort. The owner sets it for each entry of a mode's list.
- Relay does not choose a model for helpers that write or plan. They use the chat's model, by OpenCode's own rule. Only a helper that checks work is given another model.
- Relay does not run the review loop. The person, or the tool they use, decides when to check and when to fix. Relay shapes the checker.
- Not checked in the terminal app. The command runs on the server side, so it may work there, but the panel is Desktop only.
- No release of Artificial Analysis (AA) numbers to other people until the terms question is settled.

## Anti-goals (a failure even if it "works")

- A message dropped, sent twice, or changed.
- A chat moved to the agent that can change files on a decision that was unsure or missing.
- A switch the person cannot see.
- A review that never ends because every round finds new issues (the owner's words).
- Message text, file contents or images sent somewhere the person was not told about.
- A wrong price or index shown as a fact. A model with no listed price shown as "free".

## Choosing among a mode's models (added 14 Nov)

The owner asked for this after learning that the first model of a list always won: "then we make a router from the user question and code base file the jev or google decision model predict which model to use in plan , executer or reviewe". I proposed the rules below in chat and asked whether that is the router they mean. They answered "update the plan and implement it". The rules are mine.

**What the research of 14 Nov found** (tool documentation, GitHub, Hacker News and papers; Reddit and X could not be read; the figures were checked against the research notes, not against the pages):

- Routers that work label the request and then use the model a person tied to that label. Matching a request to a description that a person wrote scored 93.17% in the makers' own test, on non-coding chat ([Arch-Router](https://arxiv.org/html/2506.16655v1)). The classifier does not judge models and does not see their names ([Requesty](https://docs.requesty.ai/features/auto-routing.md)).
- Guessing "hard or easy" from the question failed in tests ([LiteLLM's own benchmark](https://docs.litellm.ai/docs/proxy/auto_routing_benchmark.md)).
- No shipped router reads code files. Files only set limits: size and pictures.
- A model change inside a chat makes the new model read the whole chat again without the cache ([Claude Code prompt caching](https://code.claude.com/docs/en/prompt-caching)).
- A reviewer weaker than the writer made results worse in one study, 91.4% to 82.8% ([LeadDev](https://leaddev.com/ai/your-ai-coding-agents-might-need-an-org-chart)).
- Nobody has measured a decision model choosing among a person's own models for coding questions. The example run of Stage 1 is the first measurement.

**The rules.**

1. **A line for each model.** Each entry of a mode's list has one line written by the owner, "use it for", of at most 200 characters. It describes requests, not the model. An entry with no line is never picked by the decider; it is used by its place in the list.
2. **Limits first, by rule.** A model is usable when it is offered right now, takes pictures if a picture is attached, and has room for the attached files. Room is a low estimate: the files' bytes divided by 4 must not be more than the model's context window. A size Relay cannot read counts as 0, and the chat so far is not counted.
3. **One request to the decider.** It holds the mode question as before, and one more `choice` question for each mode that has two or more usable models and at least one line. The choices are those lines (at most 8) and "none of these fits clearly". The decider never sees model names, prices or scores.
4. **The pick, inside the chosen mode.** One usable model: that one. No lines: the first usable model. A line answered with a confidence of 0.5 or more: its model. Otherwise the chat keeps its model if that model is usable in the mode, and else the first usable model is used.
5. **What the decider is told about files.** The names and sizes of up to 10 attached files, and how many pictures. Never what is in them.
6. **Helpers.** A helper that checks work gets its model from the Review list by the same rules. With no clear fit it gets the first usable Review model.
7. **The record** of a decision also keeps how sure the line answer was.

Not built: file contents for the decider, facts about the repository (languages, size), a "hard or easy" tier, choosing the effort, and learning from what happened after a pick.

## Proposed by me, and answered "ok update the plan" by the owner (13 Nov)

- **Relay's review helper.** One helper type, `relay-review`, which the answering model can start to check work and which Review mode also uses in the chat. Its model is the first usable model of the Review list, kept in step with the side panel. It can only read: no edits, no commands that change things, no helpers of its own. Its description tells the answering model to use it for every check of work. Writing helpers need no type of their own, because they take the chat's model.
- **Rules that make a review end**, written into the review helper's instructions and reused from the old pipeline. (1) A finding blocks only with concrete evidence of a defect or an unmet requirement. Everything else is an advisory note, and a note never causes another round. (2) Every review ends with a verdict, approve or request changes, and approves when no blocking finding remains. (3) A re-check looks only at whether the earlier blocking findings are fixed and whether the fix broke something. It is not a new full review. (4) One piece of work gets at most three checks, which is two rounds of fixes. After the third, the open problems go to the person.
- **Who holds the limit.** The limit of three checks is an instruction to the review helper. Relay also enforces it inside one review chat if Stage 0 shows that a plugin can see a helper being started. Relay cannot stop another tool that keeps starting brand-new reviews.
- **Changed after that answer (mine).** The owner's Superpowers plugin starts every helper as the `general` type, so it would not start this helper type by itself. The review helper type is now the second of two ways to give a check the Review model (see "How a check gets the Review model" below), and the limit of three checks is first tried as an instruction only. ## My calls (mine; approved with the whole document on 13 Nov, not discussed one by one)

- **What each mode means.** Plan: think, explain, investigate, design or plan; no files change. Execute: write, change, fix or run code or files. Review: check existing code or changes for mistakes and risks, and report. An ordinary question such as "explain this" is Plan. "Review this and fix it" is Execute.
- **Plan and Review cannot change files; only Execute can.** Plan and Review switch the chat to OpenCode's `plan` agent, and Execute to `build`. (I showed the read-only rule to the owner as my guess on 13 Nov; they did not object.) Relay never changes the permission settings of OpenCode's own agents. After Stage 0: when the chat moves to `plan`, OpenCode adds its own Plan-mode reminder to the next request, and when it moves back it adds a line that the Plan restrictions are over.
- **How a check gets the Review model (settled by Stage 0; the choice is mine).** Way 3, the tool hook, is built. When the answering model starts a helper, Relay sees the call before it runs, with the helper's type, its short description and its task text. Relay asks the decider the same question about the task text: plan, execute or review. For review, Relay adds the first usable model of the Review list, with its effort, to the call, and appends the review rules to the task text. The helper then runs on the Review model from its first request, on any provider. Every other helper is left alone. So is every helper when the decision fails or is unsure, and when the call continues an earlier helper, which keeps the model it started with. A call that already names a model was also left alone until 17 Nov 2026. That day's live check showed that Claude callers and Superpowers name one in every helper call, so no check was routed, and the owner chose that a check goes to the Review model even then ("yes do it"). The record notes the model the caller asked for.
  - Way 1, the resolve hook (not built). In Stage 0 it worked only for a Review model on the same provider as the chat's model. With another provider the helper failed.
  - Way 2, the review helper type (not built). It worked in Stage 0, and a plugin can create the type, but only when the calling model starts that type. Superpowers starts `general`.
  - Not tried in Stage 0: a call that continues an earlier helper, a real model as the calling model, and Superpowers' own helper prompts.
- **Review mode in the chat** gets the same review rules: Relay adds them to the chat's instructions for as long as the chat stays on the agent and model that Relay chose for Review. The panel shows the rules as text. After Stage 0: a per-chat instruction entry does this. It has to be set in the command, or in the hook that runs when a message is sent; set later, it misses that request.
- **Where the limit of three can hold.** It is counted inside one chat: the chat in Review mode, or a helper chat that is continued for a re-check. A tool that starts a fresh helper for every check keeps its own limit; Superpowers' is five rounds of fixes for each task. After Stage 0: Relay sees every helper start and can refuse one, so a limit in code is possible. It is not built first, because a plain count for each chat would also block the checks of later work.
- **A helper's requests are chat work.** OpenCode starts the helper and makes its requests inside the person's chat. They have no spending cap and are not charged to the budget ledger, like every other chat message. The decision about a helper is one more decider call (question 1).
- **Not sure means Plan.** When the decider's confidence is below 0.6, Relay uses Plan, because Plan cannot change files.
- **Execute needs a clear request, and then runs straight away.** The decider is told to choose Execute only when the message clearly asks to change, create, fix or run something now, and Plan otherwise. When it is sure, Relay switches and sends without asking first. A decision that is sure but wrong can therefore still send a question to Execute; Gate 1 measures how often.
- **No answer means no switch.** When the decider gives no answer (an error, more than 5 seconds, or no decider chosen), nothing is switched and the message goes to the chat's current model, as if `/relay` had not been typed. After Stage 0: a decider call cannot be stopped once it is made. Giving up after 5 seconds frees the chat, but the request still runs to its end and is billed.
- **What the decider is given.** The typed text (when it is longer than 4,000 characters, the first 2,000 and the last 2,000), whether the chat's agent can change files (so that "ok, do it" after a plan can be understood), the names and sizes of up to 10 attached files, how many pictures are attached, and the owner's "use it for" lines. It is never given file contents, images, earlier messages, model names or prices. (Until 14 Nov it was given only the number of files. Until 16 Nov it was given the agent's name; told "The chat is on the agent: plan", a real decider was 0.51 sure of execute for a clear fix request, so the unsure rule kept the chat on Plan. Now `plan` is described as a read-only agent and `build` as one that can change files, and other agents are not mentioned.)
- **A short list for each mode.** Relay first drops the models that are not offered right now or cannot take what is attached (a picture needs a model with image input, and files need room), and then chooses among the rest by the rules in "Choosing among a mode's models". If none is left, nothing is switched. (Until 14 Nov the rule was: the first usable model wins.) After the Desktop check: an `@` file arrives with a name and an address and no type, so Relay has to tell a picture by its name or its address. What a pasted picture looks like is not known yet.
- **Order of the calls.** Agent, then model, then the message. A step that fails is recorded, and the message is still sent. If the send itself fails, Relay reports it and does not send again, because a second send could double the message.
- **A busy chat (settled by Stage 0).** Relay never switches the model under work that is still going on. If the chat is answering when `/relay` is typed, Relay waits until it is idle, then switches and sends. Stage 0 showed why: a switch in the middle of a turn with several steps changes the model of the steps that are left. The decision can be made during the wait. Not tried: the wait while helpers are still running in the background.
- **Settings scope.** One set of mode and decider settings for all projects. The old pipeline's per-project selections are left untouched. After Stage 0: plugin storage is shared between projects, so the settings are kept there.
- **Nothing important only in memory (after the Desktop check; mine).** In the owner's profile OpenCode sets the plugins up again about once an hour. Relay keeps its settings and its record of decisions in plugin storage, and treats whatever it holds in memory as something that can vanish. What happens to a `/relay` that is waiting at that moment is not known.
- **The decider call is not charged to the budget ledger.** What Relay sends is capped as above. A decision model writes no text. An ordinary model's answer cannot be capped by Relay, so its worst case is that model's own output limit at its output price; the panel shows that worst-case figure beside the decider. This needs the owner's yes (question 1). After Stage 0: Relay's spend guard does not see a decider call, so the size cap is the only limit on it. With a decision model the worst case is small and known before the call: the capped text at the input price, which is well under a cent at $0.24 per million tokens. After the Desktop check: a decision model does report output. The free one reported 418 input tokens and 38 output tokens for one short message, so the question's own wording adds a few hundred input tokens. The worst case shown in the panel has to count both. Answered on 14 Nov: the owner wants no budget feature for `/relay` now, so the call is not reserved, and the panel shows the decider's price but no worst-case figure. The size caps stay.
- **What Relay records.** For each decision: chat id, mode, model, confidence, time taken, the cost when the host reports it, and the reason for any fallback. Never the message text.
- **Prices** come from OpenCode's own catalog. A price of 0 in and 0 out reads "$0 or not listed". The cached-input price is shown when it is above zero.
- **The index** is joined by id, never by name, from OpenRouter's copy through the models.dev id, with a visible source line. It is for the owner's own use until the terms are settled.
- **The old pipeline's code and tests stay** until the owner decides (question 4). Only its screens are hidden.
- **How the decider is called (settled by Stage 0; the choice is mine).** A decision model through the decisions call. The owner's OpenCode offers two, so no Google key is needed to start. The decisions call refuses an ordinary chat model, so the decider picker lists decision models only. An ordinary model through the text call is the fallback and is not built first: it would have to answer with exactly one word (plan, execute, review or unsure, where unsure means Plan), it gives no confidence figure, and Relay cannot cap its answer. Not yet seen: a real decision model answering a `choice` question. That takes one real request, and the owner's yes. After the Desktop check: seen. The free decision model answered in 144 ms and in 166 ms with a choice, a probability for each choice and a confidence. Not seen: the paid one, and a long message.
- **The numbers** (0.6, 5 seconds, the size caps, and the pass marks in the gates) are my starting values. The example run in Stage 1 is what tunes them.

### Stage 1b: the switch, and the terminal (added 16 Nov)

The owner, 16 Nov: "is the plan implemented if yes works on cli and the relay switch on/off". Their answers that day: the switch is per chat ("One chat at a time"), turned on with `/relay on` or the pill; the real tests run in their own OpenCode with their Ollama models and stop at $2. How it works. The probes of 16 Nov (`docs/compatibility.md`) showed each host step on 2.3.0 with a mock model.

1. `/relay on` and `/relay off` set or clear a flag for the chat in plugin storage (`relay/on/<chat id>`). They are refused in a chat that a pipeline run created, like `/relay`, and send nothing. Any other text after `/relay` is a message, as before.
2. A `prompt` hook sees every message as it is sent. When the chat's flag is on, it routes the message the way `/relay` does, inside the hook, before the message goes out: the same decider request, router, hard limits, line choice, agent and model switch, and review rules. It differs from `/relay` in three ways: an answer under 60% sure changes nothing (instead of moving the chat to Plan); a busy chat is not waited for (a 300 ms check; when busy, nothing is switched and the message goes as it is); and it never sends the message itself, because the host does.
3. `/relay` marks its own send (`metadata: { relay: 'sent' }`), and the hook leaves a marked message alone, so a `/relay` message in a chat with the switch on is decided once. The host stores the metadata with the message and does not send it to the model.
4. The hook never throws, because a throw fails the person's message (probe). Every failure becomes a note in the record, and the message goes as it is.
5. Each message the hook routes is recorded like a `/relay` decision.
6. The pill (moved here from Stage 4) sits above the chat box in Desktop, in every chat that is not a helper's. It reads "Relay on" or "Relay off". Its menu turns the switch on or off for this chat and shows the last choice in this chat. It reads and sets the flag through two new RPC methods and refreshes every few seconds while shown. A host without the pill registry loses only the pill.
7. The terminal app: `/relay`, `/relay on` and `/relay off` are server commands, so they work there too. The terminal shows no pill, and `/relay on` prints nothing there, because a plugin command cannot print. OpenCode's own "Switched to …" line shows each switch.

## Risks and unknowns

- Stage 0 ran in a throwaway OpenCode with mock models, and the Desktop check covered one throwaway command with free models. Not yet seen: a picture through the command, helpers with real models and with Superpowers' own prompts, the paid decision model, and the owner's Plannotator plugin, which acts on the `plan` agent that Relay uses for Plan and Review. Any of them can change the plan.
- Stage 0's throwaway host still read the skills in the owner's home folders, so it was not fully cut off from the real profile. The repo's smokes share that gap.
- The decider can be wrong. The "not sure means Plan" rule and the read-only `plan` agent limit the harm, and the 30 examples measure it. A wrong pick still costs a turn on the wrong model. A decision that is sure but wrong can send a question to Execute; then OpenCode's own permission settings are the only guard, as they are for any chat on the `build` agent.
- After a Plan or Review answer the chat stays on the `plan` agent, which cannot edit. A follow-up typed without `/relay` will not change files until the person switches the agent or uses `/relay`.
- A switch can move the chat to a dearer model, and it stays there for later messages typed without `/relay`. No spending cap covers these messages.
- The decider sees the message text. With Google's model that text goes to Google, and the no-cost tier's data terms were not checked. The panel must say where the text goes. The same holds for the two decision models the owner's OpenCode offers: the text goes to Ollama Cloud, or to OpenCode's own provider, and their data terms were not checked either.
- The decisions and text calls are experimental, and Desktop updates itself.
- Routing a helper depends on the decider telling a check from other work by the helper's task text. A check that is missed runs on the chat's model without the rules, and a writing helper taken for a check would run on the Review model. Gate 1 measures both.
- Relay sets the model of a helper that the person did not route with `/relay`, and adds text to its task. Both must be visible: each routed helper is listed in Recent choices, and the panel shows the rules.
- The tool hook rests on two things in OpenCode 2.3.0 that can change: the `model` field of the tool that starts helpers, and a plugin being allowed to change a tool's input before it runs. Other plugins can hook the same call; in which order they run was not tried.
- Every helper that starts costs one more decider call and waits for it, and the helper's task text goes where the decider is.
- Relay does not run the review loop, so it cannot stop a tool that keeps starting brand-new reviews. It makes each review able to end, and it limits one review chat if the host allows.
- A stricter bar means that small issues are listed as notes and are not fixed by themselves.
- A decider call cannot be stopped. A slow decider is still billed, and Relay's spend guard does not see the call (question 1).
- Choosing among a mode's models is unmeasured. No source tested a decision model picking among a person's own models for coding questions. The example run of Stage 1 is the first measurement, with made-up messages and one sample set of lines.
- A line answer's confidence is the decider's own figure, not a measured chance of being right. The value 0.5 is a starting point.
- A model change inside a chat makes the new model read the whole chat again at full price. `/relay` changes the model when a line fits clearly; with no clear fit the chat keeps its model. No spending cap covers this.
- The names and sizes of attached files now go to the decider's provider with the message text.
- If the owner's agents are customised and `plan` or `build` is missing, the agent switch fails. The message is still sent, and the record says the agent was not switched.
- Hiding the pipeline leaves a lot of code that the product no longer uses. It still has to pass its tests on every change until it is removed. Its guards also still run on every request in every chat, and they refuse the request if plugin storage fails. That suited a pipeline; it is a poor fit for a chat tool.
- On 13 Nov the owner's OpenCode background service was restarting every minute or two, and the cause was not found. A live check means little until it is steady. By the evening its log showed no errors after 20:00 UTC. The cause is still not known. After the Desktop check: two causes of restarts are now known. A config edit replaces the service within a minute, and the config and the installed plugin were edited several times on 13 Nov. The service also drops and reloads its plugins about once an hour by itself, and in the night before the check some of those reloads were followed by a restart. On 14 Nov it ran for up to 164 minutes between restarts.
- The index terms and the zero-price ambiguity are as described under Constraints.
- `/relay` only works as the first thing on a line. A person who types an `@` file first and the command after it sends a plain message with the command word in it. The panel's help text has to say so.
- Desktop does not show the agent. After a Plan or Review answer a person cannot see that the chat is on the read-only `plan` agent, so the risk above about follow-ups typed without `/relay` is easier to run into.
- OpenCode sets plugins up again about once an hour, and replaces its service after a config edit. What either does to a `/relay` that is deciding or waiting was not tried.

The question as it was asked: The repo rule says every model request the plugin itself makes must reserve its cost against the budget first. The decider call is such a request: one for each `/relay`, and one for each helper that starts. Stage 0 added two facts: Relay's spend guard does not see these calls, and a call cannot be stopped once it is made. With a decision model one decision costs well under a cent, and the free one is listed at 0. May `AGENTS.md` say that the decider's request is limited by its size and is not reserved? The other way keeps the rule but is a bigger job: the ledger today only knows pipeline runs, and a reservation is only released by evidence entered by hand (`src/cas-ledger.ts:98`, `src/cas-ledger.ts:106`), so decisions would need new ledger rules, and a budget setting would stay in the panel. Needed before Stage 1. My default is still the size limit, with only decision models allowed as the decider, because their cost is known before the call. After the Desktop check: the free decision model's two answers each reported a cost of 0, 418 input tokens and 38 output tokens.
